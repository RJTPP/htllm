## TL;DR

- **v1 is built but not qualified.** Typecheck is clean, and all unit tests pass: 103 on
  `dev`, 105 with `feat/ui-pass`. All 21 Chrome browser scenarios pass with
  `feat/ui-pass`; on `dev` the CSP scenario fails under Chrome 157. The open gates
  are live provider/MCP checks, the three-run quality gates, browser qualification, SDD
  reconciliation and release packaging.
- **New direction (decided).** Each chat is either **Chat** or **Workspace**, chosen on the
  new-chat screen and locked after that. A Workspace is a per-chat virtual folder that the
  model uses as a scratchpad and for input and output. It is not a runtime. The Knowledge
  library stays global and attaches to chats. Chat has no tools (it keeps Automatic RAG).
  All tools, MCP included, live in Workspace (§1.2).
- **Prior art.** ChatGPT now ships a Chat/Work toggle with a separate default model for
  each mode. We borrow only that **toggle pattern**. Workspace corresponds to ChatGPT's
  *Chat with files*, not to Work, which is for long multi-step deliverables. Open WebUI is
  the closest open-source design: its model sees a file list plus list/search/view tools.
  LobeHub's agent-written documents and Jan's project folders come close on writing. None
  found combines chat-scoped files the model can write with no code sandbox.
- **The most useful harness patterns** are small: reads that end with an exact "continue"
  hint, exact-match edits, old tool results replaced by short stubs, tool-call repair, and
  write permissions scoped to a path pattern. None of them need a shell.
- **Problems that matter now:**
  - Tool support is decided per provider, so any HTTP model can be put in tool mode and
    then fail with an unclear error.
  - Full tool results are replayed on every later turn.
  - Reasoning is replayed under `reasoning_content`, which Ollama ignores (confirmed in
    its source). vLLM likely ignores it too.
  - Thread delete is not atomic.
  - The SDD still describes Phase 2, and `CLAUDE.md` contains rules that are no longer true.
- **Recommended order:** small fixes and docs first (Phase 0), then two foundations that
  Workspace depends on (Phase 1), then a thin Workspace slice (Phase 2). Reconcile the SDD
  after the Workspace design settles, so it isn't rewritten twice.

Nothing blocks Phases 2–3.

**WebLLM research, answered** ([webllm-tools.md](2026-11-23-research/webllm-tools.md)).
D-13's interim rule stays: Workspace is HTTP-only. web-llm 0.2.83 has these limits:
- Native `tools` works only for five 7–8B Hermes models (4–6 GB VRAM, 4096-token context).
  I confirmed the allowlist in the installed package.
- Every reply is forced into a JSON array of calls, so the model can't answer in prose.
- Custom system prompts are rejected, and one user reports that most of the allowed models
  always return `[]`.
- A 4k context fits only one or two tool rounds.

The workable route, if in-browser Workspace is ever wanted, is our own tool-call parsing with
web-llm's `structural_tag` grammar. That needs web-llm 0.2.85 or later, which means a
dependency upgrade. It is the user's decision and should be tested live first.

## 2. As-built facts (short)

Full detail with file and line references: [research/codebase.md](2026-11-23-research/codebase.md).

- **Stack:** Astro, React, TypeScript and Tailwind, built to a static `dist/`. WebLLM runs in
  a worker. There are OpenAI-compatible HTTP providers. IndexedDB (DB v9) holds 13 stores.
  `src/services/` holds the agent loop, tools, retrieval, MCP and approvals.
- **Agent loop** (`src/services/agent.ts`):
  - 8 calls per user turn and 60 s per tool.
  - Each result is capped at min(8000 chars, remaining budget). A document page is
    4000 chars, so one turn can read at most about 32k chars.
  - There is no compaction inside a turn; it stops with a hard error when the budget runs
    out.
  - Every saved tool result is replayed as `<historical-tool-data>` on all later turns
    (`src/lib/message-context.ts`).
- **Tool gating:** `ChatProvider.capabilities.toolCalls` is set per provider: false for
  WebLLM, true for every HTTP provider. `ModelInfo.toolCalls` exists but is never set or
  read.
- **Documents** already store the full `extractedText` with `pages` as character offsets.
  Reading by line range and mapping lines to pages can be computed on the fly, with no new
  index.
- **Each thread is bound to one library** (`libraryId` has three states: unset, none, or a
  library). The composer accepts only images as attachments.
- **Tests:**
  - 103 unit tests on `dev`, 105 on `feat/ui-pass`.
  - 21 Chrome scenarios that use mocked HTTP and do not cover WebLLM.
  - A 30-task deterministic eval and one live run: evidence 45/45, absent 15/15, research
    with RAG 9/15, research with Agent 12/15, on one model.
- **No dedicated tests** for MCP, retrieval, chunking, ingest, hybrid search, the hooks or
  WebLLM. The migration test covers only v8 → v9.

## 3. Problems found

Ranked by how much they matter for the next step. "Just do" means a fix needs no product
decision.

### 3.1 Tool capability is decided per provider (affects Workspace)

Any HTTP model can be put in tool mode, and models without tool support fail with an
unclear error. Workspace availability depends on this. The fix is to fill in
`ModelInfo.toolCalls` from what the server reports and let the user override it. Sources
to check: LM Studio `/api/v0/models`, Ollama `/api/show` capabilities, OpenRouter
`supported_parameters`; a generic endpoint needs the override. *Decide*: how much to
auto-detect.

### 3.2 Reasoning is replayed under the wrong field for some servers (confirm mechanism)

`openai-compat` reads reasoning from either `reasoning_content` or `reasoning`, but sends it
back only as `reasoning_content` (`src/providers/openai-compat/index.ts:478, 589`).

- **Ollama (verified in source).** In Ollama v0.40.17 `openai/openai.go`, the message type
  has only a `reasoning` field. Incoming `msg.Reasoning` becomes `Thinking`, and
  `reasoning_content` does not appear in the file. So on Ollama, htllm's replayed
  reasoning is silently dropped between tool calls.
- **vLLM (likely, from its docs).** Its interleaved-thinking example sends `reasoning`; its
  request code was not checked.
- **LM Studio (UNVERIFIED).**
- **llama.cpp** uses `reasoning_content`.
- **DeepSeek-style endpoints** return HTTP 400 unless every replayed assistant message
  carries `reasoning_content` (Pi changelog).

Pi stores the field each reply arrived in, replays reasoning only to the same model under
that field, and drops it when the model changes. Recommend the same. This changes what the
model sees on later steps, so confirm the exact mechanism before building it, then re-run
the eval.

### 3.3 Context cost of tool results

- Full tool results, up to 8 × 8000 chars per turn, are replayed on every later turn and
  fed into compaction.
- Pages are 4000 chars and the limit is 8 calls. On local models with 8–16k context, a few
  reads exhaust the budget.
- OpenCode replaces old results with a stub (`[Old tool result content cleared]`) and keeps
  the call itself. Pi summarizes everything older than the last 20k tokens.
- Recommend stubs for results older than the last two turns. In Workspace the files persist
  anyway, so the model can read them again.
- *Confirm mechanism* for the stubs: they change what the model sees, and the measured
  Agent 12/15 used full replay, so re-run the eval afterwards. *Decide* the Workspace-only
  limits.

### 3.4 Data integrity (just do)

- Deleting a thread runs three separate transactions, so it is not atomic.
- `mcpConnections` is missing from storage stats and the storage page labels.
- Import accepts unknown thread fields without checking them.

### 3.5 Code structure (opinion)

- `App.tsx` is 934 lines and `useChat` is 896. Flag 1 of the old architecture review still
  holds, and flag 2 is only partly fixed.
- `src/lib/` reaches IndexedDB directly (`ingest.ts`, `embed-pipeline.ts`, `export.ts`).
  `export.ts` also imports from `services/`, which points the dependency the wrong way.
- I would not do a big refactor. Put the new Workspace wiring in `services/` and a small
  hook, so neither file grows.

### 3.6 Documentation drift

- **SDD (`docs/sdd/`):**
  - Every section describes Phase 2.
  - Since the baseline, 154 files have changed (+15k lines).
  - RAG, services, the agent loop, MCP and schema versions v4 to v9 are not documented, and
    §11 still says "Schema version: 3".
  - The baseline commit in `index.md` (5282806) is one commit earlier than the last edit
    (56377bb).
- **`CLAUDE.md` is stale:**
  - "No RAG or agent code in Phase 1."
  - "Five layers", with `services/` missing.
  - "The main thread never imports web-llm": dynamic imports exist, and the real rule is no
    static runtime import.
  - "IndexedDB through `src/data/` only": broken by `lib/`.
  - The commands list is missing `test`, `test:browser` and `eval`.
- **Old plan docs are stale:**
  - `architecture-review.md` still describes schema v6.
  - `phase-3-part-2-plan.md` still says "planning", although chunking, compaction and PDF
    import shipped. Persistent memory, query rewriting and the utility-model slot did not.
- Some user-facing strings still say "Agent" ("Invalid Agent setting", "Agent context
  budget reached"), and so do some docs.

### 3.7 Dead and legacy code (just do, low value)

These are unused: `Thread.toolModelKey`, `Thread.ragEnabled`, `DEFAULT_RAG_ENABLED`,
`ModelInfo.toolCalls`, and several `data/` writers that ingest bypasses. Keep
`ModelInfo.toolCalls`, because §3.1 will use it.

## 4. Research findings

### 4.1 Chat apps (detail: [chat-apps.md](2026-11-23-research/chat-apps.md))

- **ChatGPT** has a Chat/Work toggle with a separate default model per mode, and the sidebar
  can filter chats by mode.
  - Uploads and generated files go to an account-wide Library. Deleting a chat does not
    delete them.
  - No per-chat file panel is documented.
  - Users complain about sandbox resets and expired download links.
- **Claude.ai** extracts text into context. Projects switch to search near the context
  limit and show an indicator when they do.
- **Open WebUI** is the closest design. With "Preload files" off, the model gets only the
  chat's file list plus read-only tools to list, search, grep and view files. It has a
  Files tab and file cards in replies. Its docs warn that models under about 30B often
  produce malformed tool calls, and its prompt-based fallback for models without native
  tool calling is now unsupported.
- **LobeHub** "Agent Documents": notes the agent writes, kept in a side panel with history.
  This is the closest match to model-written workspace files.
- **AnythingLLM** shows how each document is used (full text, searched, or pinned) and asks
  before pruning context instead of truncating silently. LibreChat truncates at 100k
  tokens per file without saying so, which users complain about.

### 4.2 OpenCode (detail: [opencode.md](2026-11-23-research/opencode.md))

Version read: `anomalyco/opencode` (renamed from `sst/opencode`) at v1.19.6.

- **read:** output is `N: line` with path tags. Defaults are 2000 lines, 50 KB, and 2000
  chars per line. It ends with an exact "Use offset=N to continue" hint. Pointing `read` at
  a directory lists it, so there is no separate ls tool.
- **edit:** exact string replacement, which must match uniquely unless `replaceAll` is set.
  It falls back to whitespace- and indent-tolerant matching, with a check that refuses a
  match much larger than the requested text. The descriptions still claim reads are
  enforced before edits, but the code that did it was removed in April 2026.
- **Context:** old tool results can be replaced with a stub, but this is off by default.
  Oversized output is saved and the model sees a preview.
- **Permissions:** allow, ask or deny per tool and pattern. "Always" applies to the whole
  instance and offers `*`, which is too broad for us.
- **Weak models:** retries tool names lowercased, and turns invalid arguments into a plain
  "please rewrite" result.

### 4.3 Pi and the provider layer (detail: [pi.md](2026-11-23-research/pi.md))

Version read: `earendil-works/pi` (formerly `badlogic/pi-mono`) at v1.6.0.

- **Prompt and tools:** four tools (read, bash, edit, write). The system prompt is about 560
  tokens and the schemas about 600–730.
- **read:** no line numbers, a 2000-line / 50 KB cap, and hints like
  `[Showing lines 1-2000 of N. Use offset=2001 to continue.]` (verified).
- **Repair:** arguments are coerced, then validated, and errors go back as tool results.
  Before every request the transcript is repaired: results are filled in for orphaned tool
  calls, and failed or aborted turns are dropped.
- **Local servers:**
  - Ollama sends each tool call whole in one chunk and does not support `tool_choice`.
  - LM Studio and llama.cpp stream arguments in fragments.
  - Only vLLM documents `strict` schemas.
  - Recommend accumulating tool calls by `index`, with flags per endpoint that default to
    no `strict` and no `tool_choice`.

### 4.4 Browser runtimes (detail: [browser-runtime.md](2026-11-23-research/browser-runtime.md))

- **No filesystem library is needed.** Our own IndexedDB store mapping (thread, path) to a
  record, plus typed tools, carries no dependency or CSP risk.
- **Cheap functions:** papaparse (about 7 KB gzip) for CSV, and a hand-written arithmetic
  parser for the calculator.
- **Optional, `just-bash` 3.6.1** (Vercel Labs, Apache-2.0, beta; existence verified): about
  354 KB gzip, with no eval in the browser bundle. It provides grep, sed, awk, jq and find
  over a pluggable filesystem, with network off by default.
- **Optional, QuickJS** (`quickjs-emscripten`): about 231 KB of wasm. Guest code has no
  network unless we hand it a function, and memory and deadline limits are supported.
- **Blocked by our CSP** (no `unsafe-eval`): AlaSQL, Arquero, and DuckDB-wasm's worker
  paths. Pyodide is very large and its interrupt needs SharedArrayBuffer, which needs
  headers `<meta>` cannot set. Skip it.
- **Important security fact:** a `<meta>` CSP does not reach a worker loaded from a script
  URL, which takes its policy from response headers. A `blob:` worker inherits the page's
  `connect-src https:`. So running any model-written code in a worker could still send data
  out. Before any code function ships, it needs a sandboxed iframe with its own strict
  policy, or response headers. Some details of this are UNVERIFIED (Firefox and Safari
  behavior, blob workers inside a sandboxed iframe).

## 5. Workspace design sketch (opinion)

A starting point for discussion, built from the decisions plus the research. It is not a
spec. As built, it follows this sketch with the changes recorded in §9.

### 5.1 Lifecycle

- `Thread.mode?: 'chat' | 'workspace'`. The v10 upgrade sets `workspace` on threads with
  tools turned on (`agentEnabled`) and `chat` on all others (D-11). Thread validation on
  import does the same for older backups.
- The new-chat screen shows a two-option control (Chat / Workspace) with a one-line
  purpose for each. It can be changed while the chat is empty and locks on the first send
  (D-12). Switching it swaps to that mode's default model (D-21).
- Workspace requires a model marked as tool-capable (§3.1, D-23). When the current model
  isn't, the option explains why instead of hiding it.
- The sidebar shows a small mode mark on each Workspace chat.

### 5.2 Files

| Path | Source | Model can |
|---|---|---|
| `/uploads/…` | files the user attaches in this chat (text, Markdown, text PDFs) | read, search |
| `/library/<name>/…` | attached Knowledge libraries, shown live from existing documents | read, search |
| `/notes/…` (or `/outputs/…`) | written or copied by the model | read, search, write, edit |

- Store: a new `workspaceFiles` store (DB v10) holding `{threadId, path, text, pages?,
  source, version, updatedAt}`, text only. Storing original binaries for download is
  deferred.
- Library files are not copied. They resolve lazily to `Document.extractedText`.
- Checklist for a new store (from the codebase review): `db.ts` upgrade, `reset.ts`,
  `storage-stats.ts` and the storage page, export/import validation plus an orphan check,
  the thread-delete cascade (make it atomic at the same time), and a migration test.

### 5.3 Tools (eight, file-shaped)

| Tool | Behavior |
|---|---|
| `list_files(path?)` | Lists the tree with sizes and markers for read-only, uploaded and model-written files. |
| `read_file(path, offset?, limit?)` | Returns `N: line` output, capped by context window (D-24), and ends with `Use offset=N to continue` or `End of file (T lines)`. PDF pages are marked in the output. |
| `search(query, path?)` | Hybrid search (keyword plus embeddings) using the existing retrieval engine, for indexed libraries. Uploads and notes have no embeddings, so they get keyword search only. Results are capped and give `path:line` (D-15, D-16). |
| `grep(pattern, path?)` | Exact text or regex. Returns `path:line: text`, capped, with a hint to narrow the path when the cap is hit. |
| `copy_file(src, dest, lines?)` | Copies a whole input file or a line range into `/notes`, without the text passing through the model's output (D-17). The copy records its source. |
| `write_file(path, content)` | Model files only. If the file already exists, the model must have read its current version first. |
| `present_file(path, caption?)` | Delivers a file to the user. It snapshots the current version and adds a card to the reply (D-25 to D-28). It does not change the file. |
| `edit_file(path, old, new, replaceAll?)` | Exact match, unique unless `replaceAll`, with a whitespace-tolerant fallback guarded against oversized matches. It is rejected if the file changed since the model read it, which matters because the user may edit a note while the chat runs. |

- The current `list_documents`, `search_knowledge` and `read_document` are replaced by the
  `/library` view of these tools. Chat mode has no tools (D-10).
- Built-in Workspace tools are implied by the mode and kept out of `enabledToolIds`, which
  must keep holding only MCP ids.
- Attachments enter context the same way a model read does: one format and one set of caps.

### 5.4 Loop and context

- Workspace limits follow the three context bands in D-29, with a "continue" option at
  the cap. The 60 s per tool stays.
- Old results become stubs (§3.3).
- Oversized output is saved to `/notes/.tool-output/…` and the model gets a preview plus a
  pointer.
- Tool-call repair: retry names lowercased, return prose validation errors, and stop after
  3 identical calls in a row.

### 5.5 UI

- A per-chat Files side panel with three groups: uploads, notes, libraries. Each note shows
  its change history (which message changed it) and, for copies, its source.
- After regenerate or edit-and-resend, a notice says file changes from the removed turns
  remain (D-19).
- The delete-chat confirmation says "also deletes N files" (D-20).
- **Delivered files** (D-25 to D-28):
  - A card in the reply for each `present_file` call. It opens a side panel viewer at the
    presented version, with version navigation and a download button (Blob plus
    `<a download>`, as `downloadJson` does today).
  - Plain writes add no card.
  - Storage: each file keeps numbered versions. A presented version is never pruned while
    a message points to it.
- Show how each file reaches the model (full text or searched) and warn instead of
  truncating silently.

### 5.6 Functions (later, small)

1. A calculator and CSV-to-table (papaparse). These involve no code execution.
2. Possibly later: `just-bash` for richer text processing, or QuickJS. Both wait on the
   isolation work in §4.4.

Live observations (LM Studio, `gemma-4-26b-a4b-it`, 16k context, 2026-11-23):
- Reasoning streams as `reasoning_content` and tool calls stream in fragments ending
  with `finish_reason: tool_calls`. The research note had LM Studio using `reasoning` for

- `GET /api/v0/models` reports `capabilities: ["tool_use"]` and `loaded_context_length`,

Design calls made during the work (minor, within D-1 to D-31):
- D-11 migration: a chat becomes Workspace only when its Tools switch is on
  (`agentEnabled`). A chat with external tools ticked but the switch off becomes Chat.
- Seen live during work set 7: the app assumed an 8.2k context for an LM Studio model
  loaded at 16k. LM Studio reports `loaded_context_length`, so the context window could
  be filled in from it. This is a candidate for Phase 3.
- Work set 10 keeps every note version (text only). D-28 only forbids pruning presented
  versions; a pruning policy for the others can come later if storage becomes an issue.
- Work set 11b: with no switch in Workspace (D-14), ticking an external tool no longer
  turns tools off for re-confirmation. Every external call still needs approval. The
  library picker's dialog is renamed "Choose a knowledge library" so it no longer shares
  a name with the Chat panel.
- Work set 12a, the shared line model: every tool wraps lines longer than 400 characters
  (at a space when possible), so read, grep, search, copy and citations agree on line
  numbers. Text is never cut and left unreachable; PDF pages are often one long line.
- Work set 12a, grep: plain text by default. `regex=true` refuses nested quantifiers,
  quantified alternation, backreferences, more than 6 quantifiers and patterns over 200
  characters, and only the first 1,000 characters of a line are matched. Matching runs on
  the main thread, where the 60 s timeout cannot interrupt a single match, so the pattern
  guard is the protection.
- Work set 12a, citations of uploads use the workspace file id as `documentId`. Until the
  Files panel exists (work set 13), opening such a source shows "original unavailable"
  with the saved excerpt.
- Work set 13a: the side panel sits beside the chat at 1280 px and wider, and overlays
  the chat's right side on narrower windows, where there is not room for both.
- Work set 13b: an attached file locks the mode, just as a first message does, because the
  files belong to a Workspace chat. The Workspace prompt lists up to 30 current files, so
  small models know what exists without calling list_files first. Live, Gemma cited an
  upload by its path (`[[Source /uploads/trip-brief.md]]`); that resolves, because the
  existing resolver accepts a unique filename and a workspace citation's filename is its
  path.
- Work set 16: `calculate` is always offered because it is tiny. `query_csv` is offered only
  when the workspace holds a CSV/TSV and the context is above 8k, which keeps the smallest
  band's tool list near the D-30 size. Both run as plain TypeScript with no eval.
- Work set 18, proposal: uploads are covered by keyword `search` and `grep`, but not by
  meaning. Two shapes: (a) embed uploads per chat, which needs a chunk and embedding
  pipeline for workspace files and an embedding model per chat; or (b) an "Add to Knowledge
  library" action in the Files panel that reuses the existing indexing, after which the
  library's semantic search applies. (b) is much smaller and fits the global-library idea
  (D-7), but extracted PDFs would lose their page offsets unless the original is kept.
  Needs a user decision.
- Work set 3 left the unused `data/` writers (`addDocument`, `addChunks`, `addParents`,
  `saveEmbeddings` and others) in place. `lib/ingest.ts` and `lib/embed-pipeline.ts` write
  through `getDb()` instead. The right fix is to route them through those writers, which
  is a refactor of its own (the `lib/` layering in §3.5). It is not done on this branch.
